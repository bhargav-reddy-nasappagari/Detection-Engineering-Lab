# Beaconing / Periodic Callback Investigation

## Investigation Overview

This investigation evaluates suspicious process activity identified during telemetry analysis of the Beaconing / Periodic Callback simulation.

The objective is to determine whether the observed behavior resembles known attacker techniques and whether the collected evidence supports a malicious interpretation of the activity.

The investigation focuses on process execution telemetry, execution frequency, process ancestry, destination consistency, and behavioral patterns observed across the collection period.

---

# Initial Observation

During telemetry review, multiple executions of the following command were observed:

```text
curl http://127.0.0.1:8080/checkin
```

The executions appeared repeatedly throughout the observation window.

Each execution was followed by:

```text
sleep 60
```

The activity was generated by the same parent shell process.

Observed behavioral pattern:

```text
bash
 ├── curl http://127.0.0.1:8080/checkin
 └── sleep 60
```

repeating continuously.

---

# Behavioral Analysis

## Analysis of Curl Execution

### Observed Behavior

The system repeatedly launched:

```text
curl
```

against the same destination.

Characteristics:

* Same executable
* Same URI
* Same destination
* Same parent process
* Repeated execution

### Investigative Assessment

A single execution of curl is not inherently suspicious.

System administrators, scripts, package managers, and automation frameworks commonly use curl for legitimate purposes.

However, repeated execution against the same endpoint significantly changes the context.

The observed activity was not interactive.

Instead, it demonstrated a structured and recurring communication pattern.

This behavior is more consistent with automation than manual user activity.

---

## Analysis of Sleep-Based Timing

### Observed Behavior

Each callback execution was followed by:

```text
sleep 60
```

before the next callback occurred.

### Investigative Assessment

The use of sleep between network communications is a common mechanism for implementing periodic execution.

From an attacker perspective, sleep functions are frequently used to:

* Reduce activity volume
* Avoid resource consumption
* Maintain long-term persistence
* Create command-and-control polling loops

The combination of:

```text
curl
sleep
curl
sleep
curl
sleep
```

forms a recognizable beaconing structure.

---

## Analysis of Destination Consistency

### Observed Behavior

All observed callbacks targeted:

```text
127.0.0.1:8080/checkin
```

No destination changes occurred during the observation period.

### Investigative Assessment

Repeated communication with a single endpoint is characteristic of polling behavior.

In legitimate software this may represent:

* Health checks
* Monitoring agents
* Service polling
* Application status checks

In malicious operations this may represent:

* Command-and-control polling
* Beacon communications
* Task retrieval
* Operator check-ins

The telemetry alone does not reveal intent.

However, the behavior clearly demonstrates endpoint polling activity.

---

## Analysis of Execution Frequency

### Observed Behavior

Callback execution occurred approximately every:

```text
60 seconds
```

Observed pattern:

```text
14:38:11
14:39:11
14:40:11
14:41:11
...
```

### Investigative Assessment

The regularity of execution is highly significant.

Human-driven activity generally exhibits:

* Timing variation
* Irregular execution
* User interaction delays

The observed activity instead displayed:

* Consistent interval spacing
* Predictable scheduling
* Long-duration repetition

These characteristics strongly indicate automated execution.

---

## Analysis of Parent Process Behavior

### Observed Behavior

The callback activity originated from a single long-lived shell process.

Observed pattern:

```text
bash
 ├── curl
 └── sleep
```

continuously repeating.

### Investigative Assessment

The shell acted as an orchestration process.

Rather than directly performing network communication itself, the shell repeatedly launched child processes responsible for:

* Communication
* Delay
* Communication
* Delay

This behavior resembles lightweight scripting frequently used during post-compromise operations.

The shell effectively served as a simple beacon controller.

# Potential Attacker Behaviors

## Hypothesis 1: Command and Control Polling

### Supporting Evidence

Observed characteristics:

```text
Repeated HTTP requests
Consistent interval
Single destination
Long-lived parent process
Sleep-based timing
```

These behaviors closely resemble command-and-control polling mechanisms.

Example attacker workflow:

```text
Beacon starts
      ↓
Request instructions
      ↓
Sleep
      ↓
Request instructions
      ↓
Sleep
      ↓
Repeat
```

### Assessment

Strong behavioral similarity observed.

---

## Hypothesis 2: Initial Access Payload Callback

### Supporting Evidence

Many malware families establish outbound communications immediately after execution.

Observed telemetry demonstrates:

```text
Process execution
Network communication
Recurring callbacks
```

which could represent a lightweight payload establishing communications with an operator-controlled server.

### Assessment

Possible but unsupported by additional evidence.

No payload delivery or task execution was observed.

Confidence: Low

---

## Hypothesis 3: Persistence-Driven Beacon

### Supporting Evidence

The activity persisted across an extended observation period.

Characteristics include:

```text
Long-lived process
Scheduled communications
Predictable interval
```

These characteristics are commonly observed in persistence-oriented implants.

### Assessment

Behavior is consistent with a beacon maintained after compromise.

Confidence: Moderate

---

## Hypothesis 4: Benign Automation

### Supporting Evidence

Legitimate software may exhibit identical behavior.

Examples include:

* Monitoring agents
* Health-check scripts
* Service polling mechanisms
* Internal automation workflows

### Assessment

The telemetry alone cannot prove malicious intent.

The behavior is suspicious because of its structure, not because of the tools involved.

Additional environmental context would be required to distinguish legitimate automation from attacker activity.

# Investigation Findings

The investigation identified a recurring network communication pattern generated by a long-lived shell process.

The observed activity demonstrated:

* Automated execution
* Fixed timing intervals
* Repeated HTTP communication
* Consistent destination targeting
* Continuous parent-child process relationships

No evidence of payload execution, privilege escalation, credential access, lateral movement, or persistence creation was observed within the collected telemetry.

However, the communication pattern closely resembles behaviors commonly associated with command-and-control beaconing.

The strongest indicator is not the use of curl itself but the repeated execution of the same communication workflow at predictable intervals over an extended duration.

---

# Investigation Conclusion

The observed activity cannot be conclusively classified as malicious based solely on the available telemetry.

However, the behavior exhibits several characteristics commonly associated with beaconing and command-and-control communications:

```text
Long-lived parent process
Repeated curl execution
Fixed callback interval
Consistent destination
Sleep-based execution cycle
```

From a detection engineering perspective, the activity should be treated as a high-value behavioral pattern suitable for analytic development.

While individual curl executions appear benign, correlation of timing, destination consistency, process lineage, and execution frequency reveals a communication pattern that strongly resembles attacker beaconing behavior and warrants further investigation in a production environment.
